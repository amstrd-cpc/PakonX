# F-235 — what is known, and what support would take

Status (2026-11-07): **recognised, not driven.** `pakon-cli list` names an
F-235. Neither `pakon-cli` nor PakonX opens one, loads firmware into one, or
sends it a command. The F-135+ remains the only scanner this stack drives.

## Identity (shipped OEM files)

| State | USB | Firmware | Evidence |
|---|---|---|---|
| Cold (FX2 loader) | `0F05:F235`, bcdDevice `AA00`..`AA05` (Windows also prints `REV_::0x`) | `Pakon.hex` / `Pakon1.hex` / `pakon2.hex` / `Pakon5.hex` by board revision; `AA05` "USB Board Rev D DDR FIFO" → `Pakon5.hex` | `psiref/F235Driver/LDRCFG.txt`, `F235usb2.inf` |
| Warm (operational) | `0F05:35F2` REV 1 / 2 | — | `F235usb2.inf` DeviceDesc8/9 |
| F-135 family, for contrast | cold `0F05:F235` **`REV_::07`** → `Pakon7.hex`; warm `0F05:F135` | | `docs/BOOT_CHAIN.md` |

The cold identity `0F05:F235` is shared by every model. Only bcdDevice tells
an F-235 board (AA00..AA06) from the F-135 family (AA07). Before 2026-11-07
the boot script loaded `Pakon7.hex` into **any** cold `0F05:F235`. It is now
guarded: `usb::is_f235_board`, `PakonHardwareId::warm_f235` and the PakonX
Initialize check (`boot.rs` `f235_listed`) stop at an F-235.

## The OEM F-235 library: `TLA.dll`

Decompiled with Ghidra 12.1.4 through REA (2026-11-07). It has TLB's driver
family (`bDrvPutCcd*`, `bCalibrate*`, `bDriveMotor*`, DX) and more hardware
that the F-135+ does not have:
`FN_bDrvMoveFilterWheel`, `FN_bDrvMoveFilmGuides`,
`FN_bDrvMoveFilmPressureRollers`, `FN_bDrvMoveFocusSteppers`,
`FN_bDrvPutLampLevel` / `LampLevelIr` (a lamp, not the F-135+'s LED servo),
`FN_bDrvPutCcdExposures`, `FN_bCalibrateFindSmearAndFPC`,
`FN_bCalibrateFindLiteAndDark`, `FN_bLampWarmupFromStandby`,
`FN_bDrvApsFilmControl` / `ApsReadMofData` (APS).

## Decoded so far (TLA.dll 3.1.0.28, 2026-11-07)

Source: the OEM `psiref/F-X35 COM SERVER/TLA.dll`, version 3.1.0.28. A full
Ghidra 12.1.4 decompile is in `pakon-re/TLA.dll.c` (made with
`tools/re/ExportAll.java`; 1591 functions).

**Transport: the same as the F-135+.**
- `DeviceIoControl 0x222090` exchanges PPB frames: request `frame[1] + 2`
  bytes, a 64-byte reply, 2 s overlapped wait; a reply type of 1 / 3 must echo
  the request type, 7 is accepted [DIS TLA@0x1000c5d0 = FN_bDrvPacketExecuteNL,
  id 0x73].
- `0x222059` carries EZ-USB vendor requests (`IOCTL_EZUSB_VENDOR_OR_CLASS_REQUEST`;
  request 0xA0 or 0xA2..0xAC, at most 0x5000 bytes) [DIS TLA@0x1001ac60].

**PPB framing: the same frames PakonX builds.**
- `PutCommand` (id 0x7b): `[04, len, addr, 00, cmd]` [DIS TLA@0x1000dab0].
- `PutRegisterByte` (0x7f) / `PutRegisterWord` (0x81): type-2 writes of 1 / 2
  data bytes through `TLA@0x1000db50` [DIS TLA@0x1000dc10, 0x1000dda0].

**Function ids** (TLA's error-name switch, `TLA.dll.c` ~line 20380):
0x4f DriveMotorAdvanceFilm, 0x50 DriveMotorStop, 0x6b iDrvGetStepperPosition,
0x6c MoveFilmGuides, 0x6d MoveFilmPressureRollers, 0x6e MoveFilterWheel,
0x71 MoveFocusSteppers, 0x77 PutCcdExposures, 0x7c PutLampLevel,
0x7d PutLampLevelIr.

**The film transport controller is bus address `0xF4`** (the F-135+ uses PICM
0x44 / 0x24):
- **Film drive** [DIS TLA@0x100100d0]:
  - rate = register `0x85`, a word;
  - go = command `0x80` (forward) or `0x81` (reverse);
  - the rate is clamped to `[60, 2200]` when the hardware version (global
    +0x4dc) is below 1000, else `[200, 3700]`.
- **Pressure rollers** [DIS TLA@0x1000f5a0]: register `0xEE` = position 0..3,
  then 1.5 s settle.
- **Film guides** [DIS TLA@0x1000ffb0]: rollers to 3 (hardware version below
  1000) or 0, 1.5 s settle, then command `0xF4 <position>`.
- **Filter wheel** [DIS TLA@0x10033250]: command `0xE3` (film colour 1 or 8),
  `0xE4` (2 or 4) or `0xE5` (0x1000 / 0x2000); it waits for state 4 before and
  after.

`0xF4` is **not** in `protocol::kKnownControllerAddresses`, so PakonX cannot
send any of this today. Adding it is a hardware-safety change, made only with
the F-235 path and the operator's approval.

### Controllers on the PPB bus

Every byte, word and command write in TLA.dll, grouped by bus address and named
by the function it sits in (the error ids above):

| Address | Role | Registers / commands |
|---|---|---|
| `0xF0` | CCD board | through `PutRegisterCcd` only: register `0x82` (FPGA) or `0x84` (A/D), each with a sub-register |
| `0xF4` | film transport | drive rate word `0x85`, go `0x80` / `0x81`; rollers byte `0xEE`; filter wheel `0xE3` / `0xE4` / `0xE5`; focus words `0x88` / `0x8B`, home `0x87` / `0x8A`; start-up `0x9A`, byte `0x98`; sensor calibration `0xEB` |
| `0xF6` | lamp | level word `0x80`, off `0x81`, IR level word `0x90`, status `0x96` |
| `0xFA`, `0xFE` | panel / host PIC | LEDs byte `0x98` (both); `0xFE`: stop motors `0x82`, interrupt `0x86`, start-up byte `0x97`, word `0x87`; word `0x88` (extract) |
| `0x10` | USB board | data flow start `0x84` (calibration, before a scan), start-up `0x85` |

### CCD (`0xF0`) [DIS TLA@0x1000e510, 0x1002f880..0x1002fad0, 0x10032680, 0x10032d20]

`PutRegisterCcd(reg, sub, value16)` sends `[02, …, F0, 03, reg, sub, value16]`
and refuses any reg other than `0x82` / `0x84`.

- **FPGA control** = `0x82` sub `0`. A cached 10-bit word; set / clear bits:
  - `0x001` acquire (`bDrvCcdAcquireControl`);
  - `0x002` binning (FpgaSettings);
  - `0x008` exposures loaded;
  - `0x060` set once at the first FpgaSettings;
  - `0x100` IR mode (`bDrvPutCcdIrMode`).
- **Exposures** (`bDrvPutCcdExposures`): `0x82` sub `1` / `2` / `3` = R / G / B
  and sub `7` = IR, each at most `0xFFF`. The first call also writes sub `8` and
  `9` = `0x860`. Then control bit `0x008` is set. The F-235 sets a CCD exposure
  per channel; the F-135+ instead servoes LED on-times.
- **FPGA settings**:
  - `0x82` sub `4` = pixel count; sub `5` = start + count, with the window end at
    most `0x848` (`0x845` binned) and at least 6 pixels;
  - sub `6` = integration, at most `0xFF0`;
  - sub `10` = the IR window, at most integration − `0x6E`;
  - sub `0x0B` = 0 once.
- **A/D**:
  - gains `0x84` sub `2` / `3` / `4`, capped at `0x3F`;
  - offsets `0x84` sub `5` / `6` / `7`, sign-magnitude ±255 with bit 8 = negative,
    the same encoding as the F-135+ (OEM_RE §3).

### Lamp (`0xF6`) [DIS TLA@0x10033c70, 0x10032850]

- **On / level**: word `0x80`, used range `0x2CEC`..`0x3A34`. The upper limit
  also comes from a global (TLA global +0x4a4, from calibration). A request below
  `0x2CEC` turns the lamp **off** with command `0x81`.
- Each level change also moves the **filter wheel** for the film colour (1/8 →
  `0xE3`, 2/4 → `0xE4`, 0x1000/0x2000 → `0xE5`).
- **IR lamp**: word `0x90`, at most `0x5DC`.

### Focus (`0xF4`) [DIS TLA@0x100333d0]

Two steppers. Each first waits for the stepper state to be idle.
- Stepper 1: position word `0x88`, 0..`0x4D8`; position 0 = home command `0x87`.
- Stepper 2: word `0x8B`, home `0x8A`.

### Stop and image data

- **Stop**: drive stop = command `0x82` on `0xF4`; `bStopMotors` then sends
  `0x82` on `0xFE` (every motor) [DIS TLA@0x1000e4d0, 0x100015e0].
- **Image data**: overlapped `ReadFile` on a second driver handle, started in
  `bCalibrateStartDataFlow` (id 0x2b) after data flow start (`0x10` / `0x84`),
  with a reader thread `FUN_100215f0` [DIS TLA@0x10022400 region,
  TLA.dll.c ~line 24590]. The handle's path, the endpoint and the line format
  are not traced yet.

### Built from this (2026-11-07, UNVERIFIED)

- `src/pakon/protocol/f235_commands.hpp`: the frames above, each with its
  TLA address.
- `src/pakon/scan/f235_plan.{hpp,cpp}`: one film pass in TLA's order (data flow
  start → rollers → lamp level → filter wheel → IR lamp → FPGA settings → A/D
  offsets → gains → exposures → acquire → drive) and the teardown (acquire off
  → drive stop → stop motors → lamp off). It refuses inputs outside the
  decoded ranges; TLA would clamp them.
- `pakon-cli f235-plan [--ir]` prints those frames. It is a dry run: the
  example inputs are range midpoints, not calibration. Test:
  `tests/cli/scan_cli_test.cpp` (f235_plan_follows_tla…).
- **No live path.** `0xF0` / `0xF4` / `0xF6` / `0xFE` are not in the PPB
  allow-list, and nothing sends these frames.

Still to decode: the image handle, endpoint and line format; DX; the
calibration loop (`bCalibrate*`, incl. FindSmearAndFPC /
FindLiteAndDark, FindExposures, FindOpenGateExposures); lamp warm-up and
temperature (`bLampWarmUp`, `bChangeLampTemperature*`); start-up (`bInit`,
`bInit2`); the EEPROM layout.

## What driving it would take

1. **Captures.** USBPcap of the OEM software on a real F-235: boot, calibrate,
   one strip, as `docs/HARDWARE_RUNBOOK.md` did for the F-135+. Without a unit
   no command encoding can be verified, and this repo never invents protocol
   values (CLAUDE.md).
2. **TLA.dll decompilation** of the functions above, cross-checked against
   those captures: the command bytes for the filter wheel, guides, rollers,
   steppers and lamp level, and the calibration loop.
3. **A separate device path** (`scan/f235_*`): its own geometry, exposures and
   calibration. The F-135+ runner stays as it is.
4. **Boot:** the same FX2 loader mechanism, with the firmware chosen by
   bcdDevice as in `LDRCFG.txt`.
